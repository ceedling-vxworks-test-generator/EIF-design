### 今日いちばん伝えたいこと（3つ）

1. **受付は同期、結果はcallback。** `EIF_ACCEPTED` は「PCLが受け付けた」であって「終わった」ではない。結果は要求を出したConnectorにだけ、1回だけ届く。
2. **EIFは判断しない・時間で動かない・データを持たない。** 受付可否はPCL、情報の意味はREFが決める。EIFは変換と振り分けだけ（例外は差分のための前回値1か所：QA-03）。
3. **変わる理由ごとに置き場所が決まっている。** 接続相手が変わる → Connector、機種が変わる → Accessorの対応表と機種セットアップ。Frameはどちらでも変えない。

### この章の単語（聞かれたら即答）

| 単語 | 答え方 |
|---|---|
| 境界 | 外部と本ソフトウェアの出入口。外部はEIF以外のレイヤを直接呼ばない（要件 NFR-01） |
| 公開契約 | 利用者が頼ってよい振る舞いの約束。関数・引数・戻り値・呼んでよいスレッド・寿命など |

| 所有権・寿命 | 渡したデータを誰がいつまで持つか。例：イベントはcallback中だけ有効、登録した関数はプログラム終了まで有効であること |
| 再入 | ある関数の実行中に、同じ（または関係する）関数がもう一度呼ばれること。EIFではcallbackの中から要求系APIを呼ぶことを禁止している |
| thread safety | 複数スレッドから同時に呼んでも壊れないこと。要求系APIは同時に呼んでよい（10.11） |

## 3. 7章：制約事項・前提条件（0:08〜0:13）

### 話すこと（7.1 を上から）

- 「公開する要求・情報・設定・イベントは、**機種ごとの対応表に書いたものだけ**です。表に無いIDは `EIF_ERR_NOT_EXPOSED` で断ります。」
- 「`EIF_ACCEPTED` は**受付完了**です。実行完了ではありません。ここが一番大事な約束です。」
- 「完了通知は、要求を出したConnectorにだけ、最大1回届きます。」
- 「完了通知・イベント通知の中から、EIFの要求系APIを呼ばないでください。」
- 「EIFは受付可否を判断しません。PCLが断ったら、その結果をそのまま返します。」
- 「EIFは時間で動きません。定期送信やハートビートは持ちません。定期的に送りたい情報は、REFの定期通知を使います。」
- 「設定の書込み先は、今はREFへ直接です（QA-01）。PCL経由に変わっても、Connectorの作りは変わりません。」
- 「印字データは方式が未確定なので、本版の対象外です（QA-06）。」
- 「Connectorの登録は起動時だけです。」
- 7.2：「前提として、REFとPCLが先に起動していること、機種がビルド時に1つ選ばれていることが必要です。」

### この章の単語

| 単語 | 答え方 |
|---|---|
| 公開範囲 | その機種で外部に見せる要求・情報・設定・イベントの集合。Accessorの対応表に行があるかどうかで決まる |
| `EIF_ERR_NOT_EXPOSED` | 「この機種では公開していない」。APIサーバーでは501（未実装）で返す案（QA-09） |
| 受付完了 | 要求がEIFとPCLで追跡できる状態になったこと。実行が始まったかどうか、終わったかどうかは含まない |
| 要求系API | `EIF_SubmitRequest`、`EIF_CancelRequest`、`EIF_GetRequestResult`、`EIF_PatchSetting`（と`EIF_GetInfo`） |
| 時間を契機とした処理 | 定期送信、生存応答（ハートビート）、タイムアウト監視。EIFは持たない（10/20 打合せ、QA-15） |
| 定期通知 | REFの購読の通知契機の1つ（`RI_TRIGGER_PERIODIC`）。値が変わらなくても一定周期で通知が来る |
| REFへ直接／PCL経由 | 設定値の書込み方法。直接＝EIFがREFに書く。PCL経由＝PCLへ設定変更要求を出し、PCLが書くかどうかを判断する |
| `MODEL` | ビルド時に選ぶ機種名。`setup/<MODEL>/` と各Accessorの `models/<MODEL>/` が選ばれる |
| ユーザーcontext（`user_context`） | Connectorが登録時に渡す任意のポインタ。callbackにそのまま返す。Connectorが自分の状態を取り出すために使う |

### 想定Q&A

| 質問 | 答え |
|---|---|
| なぜ受付可否をEIFで判断しないのか | 要件 FR-02（製品要求の受付）と7.5で「受付可否の判定をしない」と決まっている。製品の状態を一番知っているのはPCLなので、判断を1か所に集める |
| `EIF_ACCEPTED` の後、PCLで失敗したら？ | 完了callbackで `EIF_OUTCOME_FAILED` 等が届く。受付は成功、実行は失敗、という2段階になる |
| 完了通知が「最大1回」なのはなぜ「必ず1回」ではない？ | PCLが応答しなければ届かないため（10.4.2、14章）。EIFはタイムアウトを持たない |
| callbackの中で要求系APIを呼ぶと何が困る？ | 完了callbackはPCLの要求処理スレッドで直列に呼ばれる。その中でPCLの同期APIを呼ぶと、PCLが自分の処理の終わりを待つ形になり、止まる・遅れる恐れがある。次の要求は、callbackで受け取った後、Connector自身のスレッドで出してほしい |
| REFへ直接書くのは全体構成設計 S3（REFへの書込みはPCL以下）に反しないか | その通りで、例外になる。10/20の打合せでは決まらず、当面は直接書く方針（QA-01）。後でPCL経由に切り替えられる構造にしてあり、Connectorは変わらない |
| 定期通知の周期は誰が決める？ | 機種ごとの対応表（REF Accessor）に書く。EIFが自分で周期を持つわけではない |
| 起動後にConnectorを追加できないのは不便では？ | 起動後に登録表を変えないことで、完了通知・イベント配信のたびにロックを取らずに済む（早く軽く）。動的な追加が必要になれば要件として相談したい |

## 4. 8〜9章：接続先・接続方針・機能概要（0:13〜0:21）

### 話すこと

- 8.1：「EIFの上にはConnector、下にはPCL、横にREFがつながります。印字データの格納先は未定です。」
- 8.2：「接続方針は2つです。**接続相手の違いはConnectorの中で、機種の違いはAccessorの対応表の中で吸収します。** Connectorは `eif_api.h` だけを使い、PCL・REFのヘッダーは見ません。EIFはPCLとREFの公開APIだけを使い、EXE・RSC・DEVは参照しません。」
- 図（8.2）を指して：「外部 → Connector → 公開API → Frame → Accessor → PCL・REF、という並びです。」
- 9.1の表：「何が変わったらどこを直すか、の表です。接続相手ならConnector、機種ならAccessorの対応表、PCL・REFのAPIならAccessorの共通処理、設定の書込み先なら機種セットアップの1行です。**どの場合もFrameは変えません。**」
- 9.2の表：「同期・非同期の一覧です。製品要求と取消は『受付は同期、結果は非同期』。照会・情報取得は同期。設定変更は書込み先で変わり、今の既定（REFへ直接）なら同期です。情報変化の通知は、登録しておくと非同期で届きます。」
- 9.3：「起動の順番は、REF → PCL → EIF_Setup → Connectorの登録 → EIF_Start です。誰が呼ぶかはQA-04で確定させます。」
- 9.4：「EIFがやらないことです。製品の判断、システム情報の生成や意味づけ、資源・ユニット・実機の制御、時間で動く処理、通信そのものはやりません。」

### この章の単語

| 単語 | 答え方 |
|---|---|
| 上位・下位・横断 | 呼ぶ側が上位、呼ばれる側が下位。REFは各レイヤが共通で参照するので「横断」 |
| Connector | 外部コンポーネント1つとEIFをつなぐ部品。外部形式 ⇔ 公開要求・公開モデルの変換、即時応答・遅延応答の制御を持つ。`connectors/<名前>/` |
| Frame | EIFの共通部。公開範囲の確認、要求の受付と応答先の振り分け、設定のマージ、差分の導出、配信を行う。PCL・REFの型も機種も知らない |
| Accessor | FrameがPCL・REFを使うときの接続部。PCL・REFのAPI呼出し・結果コードの変換（共通処理）と、機種ごとの対応表を持つ。`accessors/pcl/`、`accessors/ref/` |
| 機種セットアップ | 機種ごとに、FrameへどのAccessorをつなぐかを決める部分。`EIF_Setup()` を実装する。`setup/<MODEL>/` |
| 対応表 | Accessorが機種ごとに持つ表。公開ID → PCL製品要求ID、REFのID・型、変換関数 |
| 外部要求 | 外部が送ってくる要求そのもの（RESTのリクエスト、旧コマンドのバイト列、ボタン操作）。全体構成設計 4.3 |
| 公開要求 | EIFが受け付ける要求の単位。PCLの製品要求に対応する。外部要求をConnectorが公開要求に変換する |
| 製品要求 | PCLが受け付ける要求の単位（`product_request_id_t`）。全体構成設計 4.4 |
| 要求の粒度 | 1つの外部要求がいくつの製品要求になるか。旧コマンド1つが製品要求2つになる、等。Connectorで吸収する |
| 即時応答＋遅延応答 | 旧コマンドの作法。受け付けたらすぐ「受付」を返し、終わったら「完了」を返す。Connectorの中で扱う |
| 同期／非同期 | 同期＝呼出しから戻った時点で結果が確定。非同期＝戻った時点では受付だけで、結果は後からcallbackで届く |
| ライフサイクル | 起動 → 登録 → 開始 → 利用 の流れ。停止・再初期化は無い（14章、QA-07） |
| EXE・RSC・DEV | 実行制御層・資源サービス層・機器制御層。EIFからは参照しない（要件 NFR-05） |

### 想定Q&A

| 質問 | 答え |
|---|---|
| ConnectorはEIFの一部？APIサーバーの一部？ | EIFの一部（`externalInterfaceLayer/connectors/`）。APIサーバーのヘッダーを見てよいのはConnectorだけ、というルールでAPIサーバーの変更の影響をここに閉じ込める |
| FrameとAccessorを分ける意味は？ | 変わる理由が違うため。Accessorは「PCL・REFのAPIが変わる」「機種が変わる」ときに直す。Frameはどちらでも直さない。Frameの試験もPCL・REF無しでできる |
| 外部要求→公開要求の変換はEIFの責務？全体構成設計では外部が製品要求の粒度で要求する前提では？ | 旧パネルやPCインタフェースを受ける場合はその前提が崩れるので、EIF（Connector）が変換を持つ方向で北島さんと合意（QA-19。全体構成設計側の修正は北島さん） |
| 情報変化の通知はポーリング？ | ポーリングしない。REFに購読を登録し、REFから呼ばれる（購読ハンドラ） |
| 設定変更が「同期または非同期」というのは使いにくくないか | Connectorは戻り値で分けるだけ（`EIF_OK`ならその場で成功、`EIF_ACCEPTED`ならcallbackを待つ）。両方扱う作りにしておけば、書込み先が変わってもConnectorは直さない |
| 起動順はなぜQA？ | 全体構成設計 5.2は「EIFがPCLを初期化」、PCLの外部API仕様は「利用者がPCLのSetupを呼ぶ」、現行実装はPCLのStartUpがEIFを初期化、とずれている。起動処理（Main）が REF → PCL → EIF → Connector の順に呼ぶ案で合意を取りたい（QA-04） |

## 5. 10章：IF仕様（0:21〜0:39）★本題

### 10.1 初期化API（2分）

**話すこと**

- 「`EIF_Setup()` は、選んだ機種でEIFを初期化します。中では、その機種用のAccessorをFrameにつないでいます。起動時に1回呼んでください。2回呼んでもエラーにはなりません。」
- 「`EIF_Start()` で、REFへの購読を登録して受付を始めます。この後はConnectorを登録できません。」
- 「購読の登録に失敗すると、REFに解除APIが無いので、それまでの購読は残ります（QA-07）。」

**単語**

| 単語 | 答え方 |
|---|---|
| `EIF_ERR_INVALID_CONFIG` | 機種セットアップの構成不正。Accessorの関数が欠けている等。初期化時にだけ返る |
| 購読 | REFに「この値が変わったら（または定期的に）呼んでほしい」と登録すること。RIMの `RIM_Subscribe()` |
| 多重呼出し | 同じ初期化を2回以上呼ぶこと。初期化済みの状態を保ち `EIF_OK` を返す |

**想定Q&A**

| 質問 | 答え |
|---|---|
| `EIF_Setup` と `EIF_Start` を分けているのはなぜ？ | 間でConnectorを登録するため。登録が済む前に通知が来ると、届け先が無い |
| `EIF_Start` が失敗したら再試行できる？ | 状態は初期化済みのままなので呼び直しはできるが、REFに残った購読は消せない（QA-07）。現実的には起動失敗として扱う |

### 10.2 公開型（3分）

**話すこと**

- 結果コード：「`EIF_OK` は完了、`EIF_ACCEPTED` は受付完了です。この2つの違いを必ず区別してください。」
- 終端結果：「要求が最終的にどうなったかは、この6つの値で返します。`PENDING` は照会したときだけ返し、完了callbackには渡しません。」
- 識別子：「要求ハンドルは、受付に成功したときだけEIFが払い出す番号です。PCLの受付ID（generation ID）は外に出しません。稼働中は再利用しません。」
- 「公開IDの値は追加だけで、既存の値は変えません。」
- イベント：「イベントの中身はcallbackの間だけ有効です。後で使うならコピーしてください。」

**単語**

| 単語 | 答え方 |
|---|---|
| `EIF_Result` | EIFの結果コード（9種） |
| `EIF_ERR_BUSY` | PCLが受け付けない（容量・機能禁止・実行中など）、要求台帳が満杯、登録数の上限 |
| `EIF_ERR_UNAVAILABLE` | 未初期化・未開始、REF未初期化 |
| `EIF_ERR_NOT_FOUND` | 要求ハンドルが無い（終端済み・未登録）、REFに値が無い |
| `EIF_RequestOutcome`（終端結果） | COMPLETED（正常完了）、INVALID（要求が不正）、NOT_SUPPORTED（下位機能が未対応）、FAILED（実行失敗）、CANCELED（取消で終端）、PENDING（未確定。照会時のみ） |
| PCLの「ACCEPTED」 | PCLの終端状態の名前。**意味は正常完了**で、EIFでは `COMPLETED` に変換する（EIFの `EIF_ACCEPTED`＝受付完了 とは別物なので注意） |
| `EIF_ConnectorId` | Connectorの番号。登録時にEIFが払い出す（1〜4）。0は無効 |

### 10.4 Submitと完了通知（4分）★必ず話す

**話すこと**

- 「`EIF_SubmitRequest()` は、要求を出したConnector（origin）、公開要求ID、パラメータ、要求元トークン、を渡します。」

| 先着完了 | 完了が、EIFの要求台帳への登録より先に届くこと。EIFは一時的に記録しておき、登録時に要求元へ通知する |

| 質問 | 答え |
|---|---|
| 受付が同期で即時に返るのに、EIFの中にスレッドやキューはある？ | 無い。EIFはConnectorのスレッドのままPCLの受付APIを呼び、PCLの受付結果を返すだけ。非同期にしているのはPCL（受付で即時に戻り、完了時に自分のスレッドからcallbackを呼ぶ）。EIFはそのスレッドのままConnectorへ渡す |
| 完了callbackが戻りより先に来るのはバグでは？ | 仕様。PCLが同じスレッドで完了まで処理する場合などに起きる。要求ハンドルは完了callbackの引数にも入っているので、Connectorはそれを使えばよい。実装と試験で確認済み |

| EIFが「実行管理」をしていないか（要件 FR-02「実行管理を行わない」） | 台帳が持つのは「どの結果を誰に返すか」だけで、進捗や状態は持たない。応答先を覚える必要があることは10/20の打合せで確認済み（要件への追記はQA-14） |
| 同じ要求を2回送ったら？ | 2つの別々の要求として扱う（ハンドルも別）。重複を弾くかどうかはPCLが判断する |

## 12. 横断的な想定Q&A（どの章でも出うるもの）

| 質問 | 答え |
|---|---|
| 結局EIFは何をしているのか。薄くないか | 4つ。①公開範囲の確認（対応表に無いものを断る）、②要求の受付と応答先の振り分け（複数の接続先・順不同の完了・先着完了）、③型の変換と設定のマージ、④情報変化の差分と配信。判断と実行はPCL・REFに任せる |
| 現行実装から何が変わるのか | 現行はREFの購読やデータの設定がEIFにハードコードされていて、機種が変わるたびにEIFを作り直す必要があった（10/20に共有した課題）。新しい構造では、機種の違いを対応表と機種セットアップに集め、Frame・Connectorは機種で変えない |
| なぜこの構造にしたのか | 要件の「接続相手が変わってもPCL・REFに波及させない」（FR-02）と「公開範囲を製品ごとに設定できる」（FR-01）、加えて「PCL・REFのAPIが変わっても共通部を直さない」ために、**変わる理由ごとに部品を分けた**結果。共通部は自分の型だけで書き、PCL・REFへの依存は接続部に閉じ込めた |
| 機種ごとの表をFrameに渡す方式ではだめなのか | 検討した。その方式だと、差分（発生／解消）やマージを機種ごとに書く必要があり、PCL・REFの型がFrameに入る。今の方式は差分・マージを公開モデルの上で1回だけ書けば済み、Frameの試験もPCL・REF無しでできる |
| イベントキューや中継タスクを使わないのはなぜ | 早く軽く（QA-16）。タスク切替とデータのコピーが増え、EIFが遅いと製品全体が遅くなるため |
| 要件定義との整合は取れているか | 機能要件（公開範囲・変換・転送・応答・通知・PATCH・購読）と依存規則は満たしている。要件の文言とずれる点は、前回値の保持（7.5／FR-09 → QA-03）、PCL経由PATCHの5秒待ち（NFR-04 → QA-01と合わせて決める）。要件側の修正待ちとしてQA-13〜17、19がある |
| 要件の「Boundary + Adapter Layer」（7.6）とどう対応する？ | Boundary＝公開API＋Connector、Adapter＝Accessor。その間に共通処理（Frame）を置いた |
| セキュリティ（認証・権限）は？ | EIFの範囲外。外部コンポーネント（APIサーバー）側の責務 |
| ログは？ | EIFの異常（台帳満杯で捨てた等）はログに出す。製品のログ基盤（UT_LOG）へ出せる作り |
| 性能の数字は？ | 要求1件あたり、EIFの中はタスク切替なし・関数呼出しのみ。具体的な時間の要件はQA-16（応答性の非機能要件）で決めたい |

### 12.1 アーキテクチャの名前を聞かれた場合（手元だけ）

> 方針：**特定のアーキテクチャ名・パターン名は自分からは出さない。** 名前を出すと「他のパターンを採らなかった理由」に話が広がるため。

| 聞かれ方 | 答え |
|---|---|
| 「これは何アーキテクチャ？」「何かのパターン？」 | 「特定の型に当てはめたというより、要件から決めています。変わる理由（接続相手・機種・PCLやREFのAPI）ごとに置き場所を分け、共通部が外の型に依存しないようにした結果です。」 |
| 名前を挙げて「これって〇〇（例：ヘキサゴナル、クリーンアーキテクチャ、ポート&アダプタ）ですよね？」 | 「考え方として近い部分はあると思います。ただ、パターンに合わせて作ったのではなく、要件の2つの変化（接続相手と機種）からPCL・REFを守るために、この分け方にしています。」で止める。肯定も否定もしない |
| 「なら〇〇の作法どおり××にすべきでは？」 | 「その観点で問題になる具体的な場面があれば教えてください。要件と性能方針（早く軽く）に照らして判断します。」と、要件・具体例の話に戻す |
| 「他の設計案は検討したか？」 | 「機種ごとの表を共通部へ渡す方式と比べました（上の表のとおり）。差分・マージを機種ごとに書かずに済み、共通部の試験がPCL・REF無しでできる点で、今の方式にしています。」 |
