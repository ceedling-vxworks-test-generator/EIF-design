# codemap：コード構成のHTML出力ツール

Cのソースを解析して、部品ごとのコード構成を1つのHTMLファイルに出力する。Python 3.9以上の標準ライブラリだけで動く（追加のインストールは不要）。

## 使い方

```sh
python tools/codemap/codemap.py tools/codemap/eif.json -o "03.EIF設計/設計/EIFコード構成.html"
```

出力したHTMLをブラウザで開く。外部への通信はしない（ネットワークに接続しなくても表示できる）。

## 画面

| 画面 | 内容 |
|---|---|
| 構成マップ | 部品（列）ごとに、ファイル・関数・表・型定義を並べる。関数をクリックすると、呼ぶ側（青）と呼ばれる側（橙）を線と色で強調し、右に詳細（概要、実行コンテキスト、呼出し、ガード、参照している表）を出す |
| APIフロー | シナリオを選ぶと、呼出しの流れをシーケンス風のブロック図で出す。関数は縦長のブロック、呼出しは番号付きの矢印。ガード（六角形）と、参照している表・変換関数（円柱）をブロックの横に置く。同じ部品の中の補助関数は展開して、ブロックを作らない |
| 依存チェック | 部品の間の #include の数と、依存規則の違反（赤）を出す |
| 一覧 | 関数・ガード・表・型定義の一覧（ファイルと行番号つき） |

URLの # で画面を指定できる（`#map`、`#map=関数名`、`#flow=番号`、`#deps`、`#list`）。

## 解析で取り出すもの

| 対象 | 取り出し方 |
|---|---|
| 関数 | ファイルスコープの関数定義。直前の Doxygen コメントの `@brief`・`@note` と、`[C1]`〜`[C4]`（実行コンテキスト）を拾う |
| 呼出し | 直接の呼出し。構造体メンバ経由の呼出し（`control->submit()` 等）は、受け手の変数名から型を決め（設定の `receiver_types`）、その型の初期化子（`.submit = ctl_submit`）から実装を引く |
| 表 | ファイルスコープの const 配列（変換表・定義表）、static な配列（実行時データ）、関数ポインタの構造体（IFの実装表） |
| 型 | typedef struct／enum／union、関数ポインタ、別名 |
| ガード | `if (…)` の中で `EIF_ERR_*`・`UC_ERR_*`・`false` 等を return する箇所 |
| 依存 | `#include "…"`（`<…>` のシステムヘッダーは除く） |

## 設定ファイル（eif.json）

| 項目 | 意味 |
|---|---|
| `root`、`exclude` | 解析するフォルダ（リポジトリからの相対）と、除くフォルダ |
| `components` | フォルダ → 部品の対応と色 |
| `externals` | 外部（解析の対象外）の関数名の接頭辞 → レーン（例：`RIM_` → PCL／REF） |
| `lane_order` | 列・レーンの並び順 |
| `receiver_types` | メンバ呼出しの受け手の変数名 → 型 |
| `indirect_calls` | コードから決まらない呼出し（実行時に登録するcallback、表の中の関数ポインタ）を補う |
| `ignore_functions` | 図に出さない関数（mutex のロック等） |
| `async_contexts` | 非同期（別のcontextから呼ばれる）として描く実行コンテキスト |
| `flows` | APIフローのシナリオ（開始する関数と、呼ぶ側のレーン）。公開API（`entry_header` で宣言された関数）は自動で追加される |
| `dependency_rules` | 部品ごとに、include してよいフォルダと外部ヘッダー |

## 制限

- 簡易な字句解析なので、マクロで作る関数や、複雑な宣言は拾えないことがある。
- 分岐（どの条件のときにどこへ行くか）は区別しない。関数の中の呼出しを、書かれている順に並べる。例えば EIF_SubmitRequest のフローには、先着完了や台帳満杯のときだけ通る呼出しも並ぶ。
- 実行時に登録するcallbackや、表の中の関数ポインタの呼出しは、`indirect_calls` で補った分だけ出る（フローでは「※間接」と表示）。
- ガードは「if の中で特定の値を return する」形だけを拾う。
